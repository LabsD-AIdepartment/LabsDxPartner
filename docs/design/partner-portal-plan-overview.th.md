# แผนปรับ Labs D x Partner สำหรับเริ่มใช้งานจริง

เอกสารนี้เป็นคำอธิบายสำหรับเจ้าของงาน อ่านคู่กับ [แผนลงมือทำแยกงานย่อย](../superpowers/plans/2026-09-07-partner-portal.md) และ [System architecture](partner-portal-architecture.md) ซึ่งเป็นรายละเอียดอ้างอิงหลัก สถานะปัจจุบันคือการออกแบบและวางแผน ยังไม่ได้เปลี่ยน frontend หรือเชื่อมระบบจริงในงานรอบนี้

## ขอบเขตที่เหมาะกับ Labs D

ให้ดาราเข้าใจได้เร็วว่า **ทำรายได้เท่าไร เงินส่วนไหนยืนยันแล้ว จะได้รับเมื่อไร และตรวจยอดได้จากอะไร** โดยรักษาสามเมนู Overview / My content / Transactions และหน้าตา Day/Dark ที่ปรับไว้แล้ว

ระบบมีแอปเดียว แบ่งส่วนรับผิดชอบภายในชัดเจน ใช้ฐานข้อมูลสำหรับข้อมูลของพาร์ตเนอร์และข้อมูลสรุปที่เตรียมไว้ การเปิดหน้าเว็บจึงไม่ต้องรอเรียก ERP, Meta และระบบอื่นพร้อมกันทุกครั้ง ระบบต้นทางยังเป็นผู้ดูแลข้อมูลเดิมของตน

ปรับหลักเลือกเทคโนโลยีวันที่ 8 กันยายน 2026: ระบบนี้ไม่จำเป็นต้องใช้ stack เดียวกับ Sale Dashboard การเชื่อมต่ออาศัย API และรูปแบบข้อมูลที่ตกลงกัน หลังเทียบทางเลือกยังเสนอ Next.js/React เพราะรวมงานหน้าเว็บ เส้นทาง และตัวเชื่อม login ไว้ได้เหมาะกับแอปขนาดนี้ ไม่ได้เลือกเพราะระบบเดิมใช้ อ่าน [เหตุผลเลือก stack และข้อแลกเปลี่ยน](stack-fit-decision.md)

การอัปเดตอัตโนมัติ: ขณะเปิดหน้าอยู่ ตรวจเลขรุ่นข้อมูลประมาณทุก 30 วินาที แล้วดึงเฉพาะส่วนที่เปลี่ยน ตั้งเป้าทดสอบให้เห็นข้อมูลภายใน 45 วินาทีหลัง portal รับและตรวจข้อมูลสำเร็จ หยุดตรวจเมื่อซ่อนแท็บหรือ offline และตรวจใหม่เมื่อกลับมา ตัวเลขนี้เป็นเป้าหมายทดสอบ ไม่ใช่ผลวัดหรือคำรับรองว่าข้อมูลต้นทางจะใหม่ทันที

สิ่งที่เพิ่มเป็นหลักคือการเข้าใช้งานและสิทธิ์ของแต่ละคน การผูกผลงานกับข้อตกลง วิธีอธิบายยอด และประวัติรอบจ่ายที่ตรวจย้อนหลังได้ ไม่มีการเพิ่มระบบโอนเงินอัตโนมัติ ระบบซื้อขายโฆษณา หรือระบบจัดการธุรกิจแบบ marketplace

## หน้าที่ดาราเห็น

| พื้นที่ | สิ่งที่เพิ่มจาก draft | เหตุผล |
|---|---|---|
| Login | Google / LINE / Apple, รับคำเชิญ, รออนุมัติ, แจ้งปัญหาการเข้าใช้ | เข้าใช้ง่าย แต่บัญชี social ทั่วไปไม่ควรเห็นข้อมูลการเงินของใครได้เอง |
| Overview | แยกยอดประมาณการ/ยืนยันแล้ว ยอดค้างจ่าย รอบจ่ายถัดไป และวันที่ข้อมูลล่าสุด | ไม่ทำให้ยอดที่มีความหมายต่างกันดูเหมือนเป็นเงินพร้อมรับทั้งหมด |
| My content | รายละเอียดคลิปและแอด เปิดดูวิธีคิดรายได้หรือ performance เพิ่มได้ | หน้ารวมยังเรียบง่าย แต่ตรวจสอบรายละเอียดได้เมื่อสนใจ |
| Transactions | รายละเอียดรอบจ่าย เงินปรับเพิ่ม/ลด จ่ายบางส่วน เอกสารและ export | อธิบายได้ว่าทำไมยอดรายได้กับเงินเข้าจริงอาจต่างกัน |
| Account | ข้อตกลงของตน ช่องทาง login ที่เชื่อมไว้ และติดต่อผู้ดูแลพร้อมเลขอ้างอิง | มีจุดตรวจสิทธิ์และขอคำอธิบาย โดยไม่สร้างระบบ support ใหม่ |

ทุกหน้ารองรับสถานะกำลังโหลด ไม่มีข้อมูล ข้อมูลล่าช้า ข้อมูลไม่ครบ เกิดข้อผิดพลาด และไม่มีสิทธิ์ ตัวเลขที่ต้นทางยังไม่ส่งมาจะไม่แสดงเป็นศูนย์

รายละเอียดแอดเริ่มจากข้อมูลเพียง 3–4 ตัวที่มีประโยชน์ เช่น impressions, link clicks และ video views ที่มีนิยามชัดเจน ส่วนยอดที่ platform ระบุว่าเกิดจากโฆษณาจะแยกจากยอดที่ใช้คิดค่าคอมมิชชัน ค่าใช้จ่ายโฆษณาและ ROAS แสดงเฉพาะเมื่อข้อตกลงอนุญาต

## วิธีจัดส่วนของระบบ

| ส่วน | ดูแลอะไร |
|---|---|
| Identity | Social login, session, เชื่อมบัญชีและยกเลิก session |
| Partners | สิทธิ์ของผู้ใช้ ข้อตกลงและ mapping ของพาร์ตเนอร์ |
| Content | ข้อมูลคลิป แอด และ performance พร้อมแหล่งที่มา |
| Earnings | วิธีคิดค่าคอมมิชชันและผลรวมที่แม่นยำ |
| Statements | รอบจ่ายที่ตรึงยอดแล้ว หลักฐานและรายการชำระ |
| Imports | รับข้อมูล ตรวจซ้ำ ตรวจความครบถ้วน และอัปเดตข้อมูลสรุป |

ปุ่ม การ์ด ตารางสถานะ ตัวแสดงเงิน กราฟ ฟิลเตอร์ และธีมใช้ component กลางร่วมกัน หน้าแต่ละส่วนไม่คำนวณสูตรรายได้ของตัวเอง การเปลี่ยนสูตรจึงแก้ที่เดียวและมีตัวอย่างยอดที่ทดสอบร่วมกัน

ฝั่งทีม Labs D มีพื้นที่เล็ก ๆ สำหรับเชิญและกำหนดสิทธิ์ ตรวจรายการข้อมูลที่มีปัญหา ยืนยันรอบ และบันทึกการจ่ายจากฝ่ายการเงิน พาร์ตเนอร์ไม่เห็นเมนูนี้

## ทำให้ตัวเลขเชื่อถือได้อย่างไร

- ใช้หน่วยสตางค์และเลขจำนวนเต็มในการคำนวณ ไม่ใช้เลขทศนิยมแบบ JavaScript มารวมเงิน
- ออร์เดอร์เดียวที่พบทั้ง ERP และ ChatMesh นับเป็นสิทธิ์รับเงินรายการเดียว
- ยอดในหน้ารวม รายละเอียด ใบสรุปและ export อ้างชุดข้อมูลและกติกาเดียวกัน
- บันทึกว่าใช้ข้อตกลงฉบับใด อัตราใด และแหล่งข้อมูลใด ไม่เปลี่ยนอัตราย้อนหลังตามการตั้งค่าปัจจุบัน
- คืนเงินหรือแก้ข้อมูลหลังปิดรอบใช้รายการปรับยอดที่ตามรอยได้ ไม่แก้ใบสรุปเก่าเงียบ ๆ
- ถ้ารู้เพียงยอดระดับพาร์ตเนอร์ แต่ยังพิสูจน์ไม่ได้ว่ามาจากคลิปไหน จะแสดงส่วนที่ยังไม่ผูกคลิป ไม่แบ่งยอดเองเพื่อให้กราฟดูครบ
- การบันทึกว่า ERP รับออร์เดอร์แล้ว หรือ Meta นับ conversion แล้ว ไม่ใช่หลักฐานว่าเกิดค่าคอมมิชชันที่พร้อมจ่าย

## ลำดับการทำงาน

| เฟส | ผลลัพธ์ที่ตรวจรับ | เงื่อนไขก่อนเดินต่อ |
|---|---|---|
| 0 — วางฐาน | โครงสร้างแอป component กลาง รูปแบบ API และตัวอย่างการคิดเงิน | รูปแบบข้อมูลตรงกันและตัวอย่างยอดผ่าน |
| 1 — Frontend ครบ | เปิดดูทุกหน้าและทุกสถานะด้วยข้อมูลจำลองตาม API จริง | ตรวจประสบการณ์ใช้งานบนมือถือ/desktop ทั้ง Day และ Dark |
| 2 — Login จริง | Google, LINE และ Apple พร้อมคำเชิญและสิทธิ์ | ทดลองครบทั้งสาม provider และพิสูจน์ว่าข้ามไปดูข้อมูลคนอื่นไม่ได้ |
| 3 — เงินและรอบจ่าย | ข้อตกลงจริงหนึ่งราย รอบจริงหนึ่งรอบ และเอกสารที่ตรวจยอดตรงกัน | ที่มา สูตร รายละเอียด ผลรวมและ export ตรงกัน |
| 4 — เชื่อมต้นทาง | ดึงข้อมูลที่ต้องใช้จากระบบเดิม และรายละเอียดคลิป/แอด | ไม่ซ้ำ ไม่เดาที่มา มีวันเวลาล่าสุดและรับมือข้อมูลขาดได้ |
| 5 — Pilot | ทดสอบโหลด สำรอง/กู้คืน ตรวจความปลอดภัย และเตรียม release | ตรวจแยกโดย reviewer และอนุญาตการเปิดใช้งานจริงตามขอบเขต |

แผนหลักแตกเป็น 20 งานย่อย พร้อมไฟล์ที่จะสร้าง dependency และเกณฑ์ทดสอบ จำนวนงานสะท้อนจุดตรวจรับ ไม่ใช่การเพิ่ม 20 ระบบ ส่วนหน้า Overview, Content และ Transactions สามารถแบ่งทำพร้อมกันหลังรูปแบบข้อมูลและ component กลางนิ่งแล้ว

การเชื่อมข้อมูลรอบแรกอาจเริ่มจากไฟล์ที่ฝ่ายการเงินตรวจแล้ว หากต้นทางยังไม่มี API ที่ละเอียดพอ วิธีนี้เปิดให้ตรวจการใช้งานจริงได้เร็ว โดยต้องแสดงรอบอัปเดตตามจริงและไม่อ้างว่าเป็นข้อมูล realtime

## สิ่งที่ต้องยืนยันในเฟสที่เกี่ยวข้อง

ช่วง frontend ใช้ข้อมูลจำลองได้ ส่วน login ต้องตรวจบัญชี developer และ callback ของทั้งสาม provider ก่อนทดสอบจริง โดย LINE ต้องรองรับกรณีไม่มี email และ Apple ต้องทดสอบบน HTTPS ตามการตั้งค่าจริง อีเมลเหมือนกันจะไม่ทำให้ระบบรวมบัญชีหรือให้สิทธิ์โดยอัตโนมัติ

ก่อนแสดงเงินจริงต้องเลือกข้อตกลงและแหล่งข้อมูลของพาร์ตเนอร์นำร่องหนึ่งรายให้ชัด ก่อนเปิดบริการต้องยืนยัน hosting/domain/ต้นทุนและผู้ดูแล การวางแผนนี้ยังไม่ได้ตั้งค่าบริการหรือสร้างค่าใช้จ่ายเหล่านั้น
