# Report coverage and refresh due status

The existing staff import-activity endpoint now returns an optional `freshness` object per authorized connection. The shared connection panel displays how many currently tracked report windows have successfully imported data, how many do not yet have a successful report, and how many retained reports are due for another successful refresh. It does not imply all upstream data exists or that an ad's sales are complete.

The source of truth is each persisted current report window. A successful report requires both its same-window `current_generation` reference and `last_success_at`. TikTok additionally requires the generation itself to match the current connection revision: replanning can advance a window revision while retaining an older generation. That retained history does not satisfy current-connection coverage and is counted as awaiting import, without being deleted. The import writers publish these together. `imported + missing = reports`; `refreshDue <= imported`. A successful zero-result report is still a successful import, not missing data. Counts refer to scheduled windows, not individual videos, orders or commission entries. No financial calculation changes.

Refresh becomes due at `last_success_at + refresh_seconds`, using the persisted window cadence and the database evaluation clock. A failure that moves `next_attempt_at`/`next_run_at`, a provider cooldown, a retry pause or an active lease does not make old data fresh. Queue counts still explain when acquisition can run; coverage separately explains what has already arrived. A successful recent window cannot hide another missing or overdue window. `oldestRefreshDueAt` is the earliest due time among overdue imported windows, not the time a worker first failed. No arbitrary platform SLA is introduced.

Oldest/latest success timestamps describe import events, not the end date of source data. Facebook selection uses active mapping, partner, target and clip plus its recurring refresh horizon. TikTok selection uses the current schedule revision, timezone, horizon and daily windows. Obsolete windows remain stored and are excluded from current operational counts. Paused and empty accounts keep the established neutral presentation. Missing or failed activity and an old payload without `freshness` cannot imply fresh/complete reports.

This is an additive server field and a shared UI change, deployed together in the web build. New clients accept previous payloads and show coverage as unavailable. A previously loaded client with the old strict schema may reject the additive payload and show unavailable until reload; it must not render a false healthy state. There is no database migration or new runtime. Rollback reverts the projection and UI without deleting reports or affecting acquisition.

Tests use isolated synthetic generations in PostgreSQL. Both platform paths cover recent versus old imports plus a never-imported running window, independent cooldown/failure scheduling, horizon exclusion, retained old-revision TikTok generations after replanning, and revoked grants. UI checks cover partial reports, overdue retained data, missing extension and rejected inconsistent coverage. Existing queue/retry lifecycle tests remain applicable. Real provider completeness, continuous monitor installation, alert delivery and upstream entitlements are separate outstanding acceptance work.
