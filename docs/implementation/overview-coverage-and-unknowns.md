# Overview: unknown amounts and published-period coverage

G04 prerequisite, 2026-09-09. This local candidate updates the shared response and its consumers before the native Overview query is connected. It does not claim the production Overview/content APIs are implemented.

The response now distinguishes a known zero from an unknown amount. Estimated earnings are independently nullable, because a source that supplies confirmed earnings does not necessarily supply estimates. Confirmed earnings, eligible sales, unassigned amount and excluded count are null when no published window covers the request. Current unpaid obligation is independent of the selected earning window; an unknown obligation cannot establish a next payout.

`PeriodCoverage` requires complete, partial or unavailable status plus canonical covered intervals. `coverageForPeriod` intersects authoritative published windows with the request, sorts and merges adjacent/overlapping intervals, and preserves fractional-second gaps and equivalent timezone boundaries. It never derives coverage from earning/event dates or the last row. The wire output bounds coverage to 1,000 intervals; it rejects excessive fragmentation instead of truncating it. A future SQL reader must bound the publication-window query and compute coverage against the same snapshot as the amounts.

The Overview contract rejects a false completeness claim, coverage outside the requested window, unknown money presented as zero, and derived financial projections without coverage. Daily rows must be unique, ordered, fall within a covered Bangkok day, and sum exactly to confirmed earnings using integer satang. Malformed money/date input returns a validation failure rather than throwing during refinements.

The existing six-card composition, profile imagery, colors and typography remain. Shared Money renders unknown as an accessible em dash. Missing estimates and payout status have explicit text. Partial coverage has a concise warning with expandable covered windows. The shared trend chart draws separate paths across distinct covered windows instead of interpolating across an unpublished gap. One daily bucket may itself be partially covered; its value is the known subtotal, with the coverage disclosure above the cards. A true unavailable response keeps the cards and profile instead of removing them.

All repository fixture producers and consumers migrate with the required coverage field. The development Overview exposes `partial-period` and `confirmed-only` scenarios. These are excluded from the production browser build. Existing native Overview/content still use `sourceUnavailable`; there is no live Overview wire producer being silently reinterpreted. Rollback must revert this contract and its consuming components/fixtures together before exposing a native Overview route; no migration or database rollback is involved.
