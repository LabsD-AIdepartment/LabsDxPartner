# Bounded worker log capture

The existing Facebook/TikTok supervisor can retain its sanitized process events in local JSONL segments. Enable capture only on the existing `scripts/marketing-worker.mjs` process; it does not launch a second ingestion worker or change import retries, finance, provider settings or source freshness.

## Configuration and ownership

Capture is opt-in: `LABSD_WORKER_LOG_ENABLED=1` requires both `LABSD_WORKER_LOG_MAX_BYTES` (integer1,024–16,777,216) and `LABSD_WORKER_LOG_MAX_FILES` (integer1–100). There is no invented retention period or unlimited fallback. For example,10,485,760bytes and5files gives a capacity ceiling of50MiB for owned segments in that lane. This is an operator-selected example, not a guaranteed number of days. Event volume determines how far history reaches. Disabling capture preserves stdout-only behavior and existing files.

Files live under project `.agent-work/runtime/logs/<platform>/<health-port>/`. This directory is private0700; segments are0600. The supervisor claims its existing loopback health port before opening the journal. That port is the single-writer guard for its directory. Never open the same directory from another process. Separate platforms/ports use separate directories; total disk use across abandoned ports is not bounded by a single lane's policy. Operations owns old-lane retirement after deciding whether its diagnostics are still needed. Unknown files are never pruned.

Invalid/missing limit configuration stops supervisor startup before spawning an ingestion child. A filesystem failure with valid limits instead marks capture unavailable while supervision continues. The health response adds `logCapture: {state, lastStoredSequence}` only when capture is enabled. An unavailable capture makes health return503 even if the worker's process state is running. The legacy event fields and stdout JSON remain unchanged; the optional capture field describes diagnostic storage, not platform health. Core health event correlation is still matched by supervisorRunId and sequence.

## Rotation, crashes and failures

Each process opens a new monotonically numbered `events-000000000001.jsonl` segment; it never appends to a previous process's possibly incomplete final line. Readers must treat an incomplete trailing JSON line as incomplete evidence, not an event. Rotation starts a new segment before the next complete event would exceed the byte ceiling. The oldest exact-namespace segments are pruned before creation so the file-count limit includes the active segment. Existing segment sizes must fit the configured ceiling; lowering the ceiling below an existing file marks storage unavailable, preserving the file for operator review instead of silently rewriting it.

Each accepted event is written fully and fsynced before lastStoredSequence advances. Startup/rotation retain existing file contents except normal oldest-segment capacity pruning. A crash during rotation can leave a gap or empty segment, and a crash during a write can leave a partial final line. Directory entries are not fsynced; this is diagnostic retention, not a power-loss-proof audit ledger or backup. Financial history remains in the database. Synchronous small writes avoid an unbounded memory buffer but share the worker supervisor's process: a stalled filesystem can delay its event loop. Use local reliable storage and monitor loopback health externally; this is not a substitute for an independent process monitor.

On any write/rotation failure the sink latches unavailable for the rest of that supervisor run and preserves the last acknowledged sequence. It never copies raw filesystem errors, filenames or source output into health. Repair storage and restart through the existing controlled supervisor procedure; do not silently claim that missed events were recovered. Stdout remains available to an external collector. No automatic restart is triggered solely to repair logging, avoiding ingestion restart loops caused by full disks.

The sink accepts only the formatter's known envelope keys and a bounded event size. The shared formatter remains the authority for field sanitization; never pass provider payloads or arbitrary objects directly. Unsafe symlink/nonregular/hardlinked/world-readable owned files or symlinked directories are rejected. This is a service-owned directory, not a sandbox for a hostile process running as the same OS user.

## Local acceptance and remaining operations work

Focused tests force multiple rotations, verify complete ordered event tails, byte/file limits and0600 permissions, preserve unrelated files, reopen after a simulated partial-line crash, distinguish supervisor runs, and contain storage failure. Actual CLI tests cover capture disabled/enabled/unavailable with deliberately missing provider configuration: health-to-log correlation, durable stopped event where storage is available, and confirmed child/supervisor shutdown. No real provider credentials, browser database binding or continuous worker installation is involved.

Capture code and local acceptance do not choose or install a production service, alert recipient, external collector, off-device retention, storage quota or failure-history webpage. External monitoring must check unavailable/stale health as well as worker attention and report lag. Sending alerts still requires an authorized destination. No alert delivery has been claimed or performed. Rollback disables the flag or restores the previous entrypoint; retained log files and financial records need no rollback.
