|---|---|---|

ต้องกำหนดว่าดารายืนยันออกเอง หรือมีการมอบหมายที่เหมาะสมให้ทีมออกแทน โดยเฉพาะใบกำกับภาษีต้องพิจารณาเงื่อนไขของกฎหมายเพิ่มเติม
ระหว่างยังไม่กำหนด รองรับร่างที่มีข้อความ “ร่าง — ยังไม่ออกเอกสาร” ไม่มีเลขทางการ ไม่มีลายเซ็นเสมือนลงนามแล้ว

## 3. ข้อมูลตั้งต้นที่ต้องมี

### ผู้จ่าย Labs D (ตั้งค่าครั้งเดียวต่อบริษัท/สาขา)
- ชื่อนิติบุคคลภาษาไทยตามทะเบียน; ชื่ออังกฤษถ้ามี; แยกชื่อแบรนด์จากชื่อผู้ออกจริง
- เลขประจำตัวผู้เสียภาษี 13 หลัก ที่อยู่จดทะเบียน สำนักงานใหญ่/รหัสสาขา
- สถานะ VAT และวันที่มีผล; รายละเอียดทะเบียนที่ฝ่ายบัญชีรับรอง
- ผู้รับผิดชอบเอกสาร ช่องทางติดต่อ และผู้มีอำนาจออก/ลงนาม
- บริษัทใดเป็นคู่สัญญาและผู้จ่ายเงิน เมื่อแบรนด์หลายแบรนด์อยู่ต่างนิติบุคคล

### ผู้รับเงิน (เก็บต่อคู่สัญญา ไม่ผูกกับชื่อเล่นบนโปรไฟล์)
- บุคคลธรรมดา / นิติบุคคล / เอเจนซี่ที่เป็นคู่สัญญา; ชื่อจริงหรือชื่อนิติบุคคล
- เลขผู้เสียภาษี ที่อยู่ สาขา และสถานะ VAT พร้อมวันที่มีผล
- หากเป็นเอเจนซี่: ใครเป็นผู้ให้บริการ ใครเรียกเก็บ ใครรับเงิน ใครถูกหักภาษี ต้องไม่อนุมานจากบัญชีธนาคาร
- ข้อมูลบัญชีรับเงินเมื่อจำเป็นกับเอกสาร; จำกัดการเห็นตามหน้าที่
- ผู้มีอำนาจออกเอกสาร/ผู้รับมอบหมายและหลักฐานขอบเขตอำนาจ

### ต่อดีลและประเภทรายได้
- ประเภทค่าตอบแทน: คอมมิชชัน ค่าบริการ/รีวิว ค่าโฆษณา ค่าใช้ภาพ/สิทธิ โบนัส ฯลฯ
- หมวดเงินได้ ฐานภาษี วิธีคำนวณ/ผู้รับภาระภาษี อัตราและช่วงวันที่ใช้ ตามฝ่ายบัญชีกำหนด
- ราคาตามสัญญารวม VAT หรือยังไม่รวม; ส่วนลด และวิธีปัดเศษ
- เงื่อนไขออกใบแจ้งหนี้ วันครบกำหนด การแบ่งจ่าย และเงื่อนไขรับรองการจ่าย
- ไม่ตีความ Organic/Brand ads เป็นประเภทภาษีโดยอัตโนมัติ และไม่ hardcode WHT 3% / VAT ทุกดีล

### เอกสารเดิมที่ช่วยทำให้ตรงธุรกิจ
- ตัวอย่างที่ฝ่ายบัญชีใช้อยู่: ใบแจ้งหนี้ ใบเสร็จ ใบกำกับภาษี 50 ทวิ อย่างละหนึ่งชุดเท่าที่มี ปิดข้อมูลส่วนตัวได้
- รูปแบบเลขเอกสาร ปี พ.ศ./ค.ศ. รอบเริ่มนับใหม่ เลขล่าสุด/ระบบเดิมที่จะหยุดใช้ เพื่อไม่ออกเลขซ้ำ
- โลโก้ต้นฉบับ และข้อกำหนดหัวกระดาษ; ใช้แบรนด์เดิมจากโปรเจ็กต์เริ่มออกแบบได้
- ข้อมูลทดสอบหนึ่งเคสจ่ายครบ หนึ่งเคสจ่ายบางส่วน หนึ่งเคสมีปรับปรุง พร้อมยอดที่บัญชีคาดหวัง
- ผู้ตรวจจากบัญชีหนึ่งคน; ไม่ต้องขอให้ owner ส่งรหัสผ่าน token กุญแจลงนาม หรือบัตรประชาชนเต็มใบในแชต

## 4. หน้าตาและ component เอกสาร

ชุดตั้งค่ากลาง DocumentTheme / CompanyProfile / CounterpartyProfile / TaxPolicy / DocumentSeries / TemplateVersion แยกจากหน้าจอและแยกจากกัน
องค์ประกอบใช้ร่วม: DocumentHeader, PartyBlock, DocumentMetadata, LineItemsTable, TaxSummary, PaymentSummary, SignatureBlock, DocumentFooter

- กระดาษ A4 พื้นขาว ตัวหนังสือเข้ม ใช้สีเขียวแบรนด์เพียงหัวข้อ/เส้นเน้น; เอกสารไม่เปลี่ยนเป็นพื้นดำตาม Day/Dark ของเว็บ
- ฟอนต์ไทยฝังในไฟล์และเลือก/ค้นหาข้อความได้; เริ่มตัวอักษรเนื้อหาขนาด 12pt (16px ที่ 96dpi) ทดสอบพิมพ์จริง ไม่ย่อทั้งเอกสารเพื่ออัดให้เหลือหน้าเดียว
- ตารางจำนวนเงินชิดขวา ทศนิยมสองตำแหน่ง คอลัมน์หน่วย/อัตรา/ฐานภาษีมีความหมายชัด
- หัวตารางซ้ำทุกหน้า หมายเลขเอกสาร/เลขหน้า แยกกลุ่มยอดรวมและลายเซ็นไม่ให้ขาดกลางหน้า; ชื่อและที่อยู่ยาวขึ้นบรรทัดได้
- รายงานหน้าแรกเป็นสรุปและกราฟ ส่วนรายละเอียดเป็นภาคผนวก; ระบุช่วงวัน timezone Asia/Bangkok ตัวกรอง และข้อมูลถึงเมื่อใด
- แยก “ไม่มีข้อมูล” จาก 0; รายได้ยืนยัน/ประมาณการและยอดจ่ายต้องแยกป้ายชัด
- 50 ทวิรักษาช่องและข้อความขั้นต่ำตามแบบกรมสรรพากร ไม่ย้ายจนเปลี่ยนความหมายเพื่อความสวยงาม
- ใบสรุปงวดกับรายงานที่ export จากช่วงหน้าจอเป็นคนละเอกสาร อย่านำตัวกรองหน้าจอไปตัดรายการของใบสรุปทางการ

## 5. ขอบเขต module และเจ้าของข้อมูล (Change Mode)

- B1/B2: เพิ่มการจัดทำรายงานและการออกเอกสารใน Portal; การสั่งโอนเงินจริงและการยื่นภาษีอัตโนมัติยังไม่รวมในงานนี้
- B3/B4: report-query adapters -> document snapshot/contracts -> renderer/templates; issuance service ใช้ snapshot ที่ตรวจแล้ว; UI เรียก service ผ่าน API
- B8: earnings/settlements เดิมยังเป็นเจ้าของยอดรายได้และหลักฐานจ่าย; document registry เป็นเจ้าของเลขเอกสาร ฉบับที่ออก snapshot/template version และประวัติยกเลิก; accounting policy เป็นเจ้าของการจำแนกและวิธีภาษี
- B9: server ตรวจ partner membership และสิทธิ์เอกสารทุกครั้ง; กำหนดสิทธิ์ดูร่าง/ออกเอกสาร/ยกเลิก/ข้อมูลภาษีแยกกัน ไม่ถือว่า marketing มีสิทธิ์ทั้งหมด
- B10: ฝ่ายบัญชียืนยันข้อมูลภาษีและสิทธิผู้ออกก่อนเปิดออกจริง; ทีมพัฒนารับผิดชอบ render/archive/download/ตรวจยอด/กู้คืน
- B5/B6/B7: อยู่ codebase เดิม ไม่สร้าง microservice โดยไม่มีเหตุผล; งาน render มี concurrency/timeout/ขนาดจำกัด แยกขอบเขตทรัพยากรจาก request และ DB transaction; จะย้าย worker เป็น process แยกเมื่อวัดความจำเป็นได้

เลือก engine PDF หลังทดสอบ Thai shaping, pagination, font embedding, runtime size และ deployment portability; ไม่เอา browser session ของ owner ไปเป็น backend generator
renderer รับข้อมูลที่ผ่านการตรวจและ asset ท้องถิ่น/ที่ควบคุมเท่านั้น ไม่มี user HTML/remote URL ไป fetch เอง

## 6. ความถูกต้องและวงจรเอกสาร

1. สร้างร่างจาก version ของรายได้/การชำระที่ชัดเจนและโปรไฟล์ภาษีที่มีผลในวันรายการ
2. ตรวจข้อมูลจำเป็นตามประเภทเอกสาร พร้อมแสดงสิ่งที่ขาดเป็นรายการ ไม่บังคับข้อมูลทางภาษีเพื่อดูรายงานทั่วไป
3. ตรวจยอดด้วย integer minor units / decimal ที่กำหนด precision; ไม่ใช้ floating point รวมเงิน และไม่คำนวณย้อนหลังโดยใช้อัตราปัจจุบัน
4. ภาระชำระเดิม: cash + withholding + other = obligationSettled; ภาษีหัก ณ ที่จ่ายไม่ใช่เงินสดที่ดารารับจริง
5. ยอดเอกสารบริการ: ฐานหลังส่วนลด + VAT = ยอดก่อนหัก; WHT ใช้ฐานตามนโยบายที่ตรวจแล้ว (อาจต่างจากฐาน VAT); เงินที่โอน = ยอดก่อนหัก - WHT - ส่วนที่ชำระ/หักอื่นตามการจัดสรรที่ยืนยัน
6. เมื่อไม่มีข้อมูล VAT ในยอดต้นทาง ห้ามบวก VAT เข้า statement เดิมทันที ต้องกำหนดว่า obligation เดิมรวม VAT หรือไม่และทดสอบ reconciliation ก่อน
7. ออกเอกสารด้วย idempotency key + unique key ต่อผู้ออก/สาขา/ประเภท/series/period; ล็อกเลขและบันทึก snapshot/audit atomically
8. จองเลขที่แล้วไม่ใช้เลขนั้นซ้ำเมื่อ render ล้มเหลว; เก็บ render-pending/failed และ retry เอกสารเดิม ไม่สร้าง invoice ซ้ำเมื่อผู้ใช้กดอีกครั้ง
9. เก็บ original PDF bytes/hash/templateVersion/source revisions; ดาวน์โหลดซ้ำเป็นไฟล์ฉบับเดิม ไม่ render ด้วยข้อมูลบริษัทที่แก้ภายหลัง
10. แยก draft / issued / cancelled และ render state; การแก้ไขหลังออกจริงต้องใช้วิธีที่ตรงประเภทเอกสาร เช่นใบเพิ่ม/ลดหนี้ ใบแทน หรือยกเลิกตามกระบวนการ ไม่ overwrite
11. รายงานปกติสร้างใหม่ตาม as-of ได้ แต่ต้องระบุเวลาชุดข้อมูล; export ทุกหน้า/ทุกรายการที่อยู่ในช่วง ไม่ export แค่หน้าที่เปิดอยู่
12. ใบเสร็จอาศัยการรับชำระที่ยืนยันแล้ว; 50 ทวิอาศัยการหักจริง ไม่ออกจาก estimated earnings; ตรวจ partial payment และ reversal ก่อนออก
13. PDF ปกติไม่อ้างว่าเป็น e-Tax Invoice/e-Receipt ที่เข้าโครงการแล้ว: แยกช่องทางลงนาม/ส่งมอบ/นำส่ง/เก็บรักษาตามระบบที่บัญชีเลือก

- authenticated export API: scope/version validation, private no-store, filename, size/timeout/concurrency limits
- ยังไม่เรียกใบสรุปว่า invoice/receipt และไม่เติมเลขภาษีสมมุติในเอกสารจริง
- จบเมื่อดาวน์โหลด PDF จากเว็บได้ ข้อมูลครบทั้งช่วง ตรงกับหน้าจอ/statement ตามความหมายที่เลือก และตรวจทุกหน้าที่ render ทดสอบแล้ว

D02 — ข้อมูลการเงินและร่างเอกสาร
- company/counterparty tax profile version, tax policy effective date, series setup; shared form ไม่ hardcode ต่อพาร์ทเนอร์
- ตัวอย่าง invoice/receipt/50ทวิข้อมูลสมมุติแสดง DRAFT ชัด พร้อม required-field validation และรายการสิ่งที่ยังขาด
- จบเมื่อบัญชีตรวจหนึ่งเคสบุคคล หนึ่งเคสนิติบุคคล และกรณีไม่จด VAT แล้วข้อมูล/บทบาทผู้ออกถูกต้อง

D03 — ออกเอกสารหลักและคลังเอกสาร
- registry/immutable snapshots/numbering/idempotency/archive/version/download/revoke permissions/audit
- การออกเอกสารในนามดาราต้องใช้ทางเลือกที่ owner ตอบและอำนาจที่บัญชียืนยัน
- เลือกช่องทางเอกสารกระดาษหรืออิเล็กทรอนิกส์ให้ชัด; ถ้าต้องเป็น e-Tax ให้ทำข้อกำหนดช่องทางนั้นก่อนเปิดใช้
- จบเมื่อออก/ดาวน์โหลด/กดซ้ำ/ออกพร้อมกัน/ล้มเหลวแล้ว retry/ยกเลิก/partial payment/reversal ถูกต้อง และไม่มีข้ามสิทธิ์

D04 — เปิดใช้งานกับบริษัทและดีลจริง
- ตั้งค่าเลขเริ่มต้น/cutover จากระบบเก่า สำรองและทดสอบกู้คืนทะเบียน+ไฟล์ พร้อมผู้รับผิดชอบและขั้นตอนส่งมอบเอกสาร
- ตรวจเรื่องรูปแบบ/ภาษี/สิทธิผู้ออกโดยบัญชีบนตัวอย่างจริง ก่อนเปิด issue ให้ผู้ใช้งานจริง
- ผลตรวจไม่เท่ากับยื่นภาษีสำเร็จ; การยื่นและระบบภายนอกต้องมีหลักฐานแยก

ทำทีละ task แล้วรายงานหยุดก่อนถัดไปตามความต้องการ owner; ไม่ย้อนทำ account/login

## 8. ทดสอบ/ความเข้ากันได้/rollback

- กรณีหลัก: ข้อความไทย/ชื่อที่อยู่ยาว ข้ามหน้า พันรายการ/empty/missing; ตัวกรองสิ้นสุดแบบ exclusive; ยอดเงินสูง/สตางค์/ลบ/คืนเงิน; VAT/non-VAT/WHT หลายฐานตามข้อมูลตัวอย่างบัญชี
- ทดสอบ immutable statement เทียบ full export, source version เปลี่ยนระหว่างสร้าง, user ถูกถอนสิทธิ์ระหว่างรอ, concurrent numbering, duplicate click, render/storage timeout
- หน้าเว็บ preview และ native ใช้การจัดหน้าเดียวกันแต่แยกแหล่งข้อมูล; ห้าม fixture หลุด production
- เพิ่มสัญญา PDF แบบ additive; รักษา CSV เดิมจนยืนยัน consumer ไม่ใช้ ไม่เปลี่ยน MIME CSV เงียบ ๆ
- schema ใหม่ต้องเป็น migration ใหม่ ไม่แก้ migration ที่ใช้แล้ว; local test ก่อน target จริง และอ่าน gitcommand ก่อนทำ migration/deploy
- rollout ปิดการออกจริงก่อน เปิดรายงาน/ร่างได้แยก; rollback ปิด issue ใหม่ คงดูเอกสารเก่าและ registry ไว้ ห้ามลบเลขหรือ rollback DB เพื่อ reuse เลข
