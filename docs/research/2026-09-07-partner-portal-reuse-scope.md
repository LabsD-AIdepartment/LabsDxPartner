## ข้อสรุป

**สร้างหน้าส่วนตัวสำหรับพาร์ตเนอร์บนข้อมูลและงานบัญชีของ Labs D ที่มีอยู่แล้ว** มีสามหน้าเดิม: Overview / My content / Transactions ความน่าเชื่อถือมาจากตัวเลขที่ตามกลับได้ สูตรที่อ่านเข้าใจ ยอดปิดรอบที่ไม่เปลี่ยนเงียบ ๆ และหลักฐานการจ่าย ไม่จำเป็นต้องมีจำนวนฟีเจอร์เท่า Shopify หรือ Shopee

ไม่จำเป็นต้องตัดสินโมเดลค่าจ้างใหม่ทั้งหมดก่อนออกแบบ portal: ใส่ข้อตกลงที่ Labs D เจรจารายคน เช่น SKU/ยอดที่เข้าเงื่อนไข อัตรา วันเริ่ม–สิ้นสุด และรอบจ่าย หากมีค่าจ้าง/โบนัสให้นำเข้าบรรทัดที่อนุมัติแล้ว ไม่สร้างเครื่องคำนวณสัญญาอิสระทุกประเภท

## เติมเพียงสามกลุ่มข้อมูล

เป็นกลุ่มข้อมูลเชิงหน้าที่ ไม่ใช่คำสั่งให้สร้างสาม service หรือสามฐานข้อมูล จะวางเป็นส่วนเล็กใน backend ที่เลือกใช้ร่วมกันได้

1. **ดาราและข้อตกลง:** บัญชีใดเห็นข้อมูลพาร์ตเนอร์ใด; สินค้า/คลิป/ad/link/code ที่ผูกไว้; ช่วงวันที่; ฐานคิดและอัตราที่ตกลง มีหลักฐานการเปลี่ยนเงื่อนไข ไม่ต้องมีระบบร่างสัญญาหรือ e-sign ใหม่
2. **รายการรายได้ที่อธิบายได้:** เลขอ้างอิงต้นทาง → ยอดเข้าเงื่อนไข → อัตรา → รายได้ → สถานะ/เหตุผลปรับ พร้อมข้อตกลงที่ใช้ คงความละเอียดเงินจากต้นทาง ไม่ดึงยอด headline ที่ปัดเป็นบาทเต็มมาทำ statement
3. **สรุปรอบและผลจ่าย:** เก็บสำเนางวดที่อนุมัติ จำนวนเงิน/รายการประกอบ วันจ่ายและหลักฐานจากงานบัญชีเดิม หากแก้ภายหลังให้เห็นรายการแก้และยอดใหม่โดยเก็บฉบับเดิม ไม่คำนวณประวัติทุกงวดใหม่จากเรตล่าสุด

ถ้าต้นทางยังส่งได้เพียงยอดงวดที่รับรองแล้ว เริ่มด้วยการนำเข้ายอดงวดพร้อมไฟล์แจกแจงจริงได้ ต้องบอกระดับข้อมูลให้ตรง ไม่แสดงรายออเดอร์หรือรายคลิปที่ไม่มีหลักฐาน ระบบเล็กไม่ได้หมายถึงใช้ยอดที่เดามา

ส่วนควบคุมภายในต้องมีเพียงการผูกพาร์ตเนอร์/เงื่อนไข ตรวจและเผยแพร่งวด และบันทึกหลักฐานจ่าย สามารถใช้หน้าภายในหรือ import ที่ควบคุมสิทธิ์ ไม่ต้องสร้าง admin suite ใหม่ ดาราอ่านข้อมูลเหล่านี้ผ่าน API ที่จำกัดตามบัญชีฝั่ง server

## มาตรฐานความน่าเชื่อถือแบบขนาดเล็ก

1. **รวมยอดกลับได้:** จากยอดใหญ่ไปถึงรายการหรือไฟล์แจกแจงต้นทาง มีเลขอ้างอิงและเวลาอัปเดต
2. **รู้สูตรของตัวเอง:** เห็นฐาน อัตรา และช่วงที่ใช้ ไม่จำเป็นต้องเห็นต้นทุนหรือข้อมูลพาร์ตเนอร์อื่น
3. **ไม่ปนสถานะ:** ยอดประมาณ / ยืนยันรอจ่าย / จ่ายแล้ว แยกชัด; “ส่งเข้า ERP แล้ว” ไม่ใช้แทนการรับเงินหรือจ่ายค่าคอม
4. **แก้แล้วมีเหตุผล:** คืนบางส่วน การปรับ และงวดที่เคยจ่ายยังตรวจย้อนหลังได้ ไม่หักคืนสองครั้ง
5. **เงินโอนมีหลักฐาน:** งวดจ่ายแยกจากวันที่เผยแพร่คลิป ยอดหักและเงินสดตามเอกสารบัญชี; ยอดจ่ายบางส่วนยังมีส่วนค้าง
6. **เห็นเฉพาะสิทธิ์ของตน:** server จำกัด partner scope ไม่อาศัยตัวกรองหน้าจอ ไม่ส่งแชต ชื่อ/เบอร์/ที่อยู่ลูกค้า หรือข้อมูลทั้งบริษัทไปให้ดารา

นี่คือคุณสมบัติที่ตรวจรับได้ ไม่ใช่การอ้างว่าได้รับการรับรองหรือมีความน่าเชื่อถือเทียบเท่าผู้ให้บริการระดับโลกแล้ว

## ช่องว่างที่ต้องเชื่อมจริง มีขนาดจำกัด

- **ยอดบริษัท → ยอดพาร์ตเนอร์:** feed ERP ของ Sale Dashboard ปัจจุบันมี company grain `pageId=0` จึงใช้ยอดรวมนี้แบ่งให้ดาราไม่ได้ ต้องรับรายการ/ยอด SKU ที่อยู่ใน scope จริง หรือไฟล์แบ่งยอดที่ผู้รับผิดชอบตรวจแล้ว เพิ่มข้อมูลเฉพาะตรงนี้เมื่อจำเป็น
- **สื่อ → สิทธิ์รับเงิน:** Sale Dashboard มี ad/creative IDs แต่ต้องเพิ่ม mapping เข้าดาราและเงื่อนไข โดยหนึ่ง content อาจถูกใช้หลาย ad; mapping ไม่ได้พิสูจน์ว่าออเดอร์เป็นของคลิปนั้นเสมอ
- **แชต → ออเดอร์:** ChatMesh มี ERP reference ที่ใช้ต่อได้ แต่ source ยังระบุว่า `closing_touchpoint_id` ว่าง และ reader touchpoint บางส่วน join PSID อย่างเดียว ต้องไม่ใช้เส้นนี้คำนวณจ่ายอัตโนมัติจนเช็ก Page และหลักฐานของรายการที่เลือกแล้ว ไม่จำเป็นต้องรื้อ ChatMesh ทั้งระบบ
- **บัญชีภายใน → ดารา:** API ภายในปัจจุบันไม่ใช่ partner API; `getUserScope()` ใน Sale Dashboard ยังคืน `all` การใช้ระบบ login เดิมจึงไม่พอ ต้องมีทางอ่านเฉพาะรายก่อนเปิดให้ดารา
- **แหล่งตัวเลข → เงินปิดงวด:** แยก Meta performance, ERP order facts และผลจ่ายดารา ดูรายละเอียดได้โดยไม่บวกยอดออเดอร์ที่ปรากฏทั้ง ERP และ ChatMesh ซ้ำ

## ทำเป็นสามงานที่จบได้

**งาน 1 — เลือกพาร์ตเนอร์ตัวอย่างหนึ่งคนและงวดหนึ่งงวด:** ใช้ข้อตกลงจริงที่มีอยู่ เลือกแหล่งยอดหลักของงวดนั้น หาเลขอ้างอิงและหลักฐานที่ทำให้รายการรวมตรงกับผู้ดูแล ระบุสิ่งที่รู้แค่ระดับงวด/ดารา/คลิปตามจริง งานนี้ตัดสินได้ว่าจะต่อข้อมูลเดิมตรงไหน โดยไม่ต้องเลือก business model ทั้งบริษัทใหม่

**งาน 2 — เติมทางอ่านเฉพาะพาร์ตเนอร์และรายละเอียดในสามหน้า:** ใช้ระบบเดิมเป็นต้นทาง เพิ่ม mapping + รายการรายได้ + snapshot งวดตามความจำเป็น ข้อมูลแบบประมาณกับงวดอนุมัติแยกกัน ไม่มีการโอนเงินอัตโนมัติหรือเขียนกลับออเดอร์

**งาน 3 — ให้ดาราและผู้ดูแลตรวจงวดเดียวกัน:** ตรวจยอดรวม→รายละเอียด→สูตร→เงินจ่าย, เปลี่ยนช่วงวันแล้วยอดรอบจ่ายไม่ผิด, คืน/จ่ายบางส่วนไม่หักซ้ำ, รับข้อมูลซ้ำไม่เพิ่มเงิน, อีกบัญชีอ่านไม่ได้ และข้อมูลเก่าแสดงวันอัปเดตตรง จากนั้นค่อยเพิ่มพาร์ตเนอร์หรือแหล่งข้อมูลที่จำเป็นจริง

สิ่งที่ตัดออกจากขอบเขตแรก: สร้าง ERP/ท่อข้อมูลยอดขาย/Ads Manager ซ้ำ, payout gateway/wallet, ระบบรับสมัคร affiliate จำนวนมาก, campaign marketplace, ระบบร่างสัญญา/อนุมัติคอนเทนต์เต็มชุด, tier engine หลายแบบ, AI แนะนำหรือชี้ขาดเงิน และระบบ ticket ใหม่ งานบริการ/สินค้า/กฎหมายที่บริษัทต้องทำยังคงทำผ่านทีมและเครื่องมือเดิมได้
