# Unattended local service monitoring

The optional service monitor repeatedly checks only explicitly configured same-host services. It reuses the existing worker health interpretation and reads web liveness then readiness. It does not call platform APIs, restart services, change financial data, or send messages. Unconfigured platform workers are absent rather than failed. Healthy processes do not establish source coverage, correct commission, or external platform access.

Run the same Node runtime as the web. Assign a unique explicit monitor port and a port for each installed target. Check listeners and their owning projects first; never assume default worker ports are free. Here port4191 belongs to another project and is not a monitor target.

```sh
LABSD_MONITOR_PORT=43200 LABSD_MONITOR_WEB_PORT=4188 node --import tsx scripts/service-monitor.ts
```

The example assumes the intended web actually listens on4188; replace ports with verified values. `npm run services:monitor` is a convenience wrapper with project-local temporary/cache settings. A process manager should invoke the direct Node command so SIGTERM targets the monitor itself. Set `LABSD_MONITOR_FACEBOOK_PORT` and/or `LABSD_MONITOR_TIKTOK_PORT` only for running worker health listeners. TikTok means Shop video, not paid Ads. Duplicate ports, missing targets, invalid values or listener conflicts fail without probing targets. No credentials/environment dump is needed.

Defaults:30seconds after each completed cycle,3seconds per request. Interval accepts1–300seconds; timeout0.1–10seconds. Up to3 targets run concurrently; cycles never overlap. Liveness failure skips readiness; readiness503 remains unavailable. Fixed HTTP loopback web paths, no redirects,1KiB body limit and absolute deadline; workers retain their8KiB bound. This checks the same-host upstream, not TLS/DNS/proxy/CDN/off-host availability. Add a trusted external probe at deployment for those surfaces.

`GET/HEAD http://127.0.0.1:<monitor-port>/health` returns200 only when a recent completed cycle found every configured target healthy.503 covers starting/stale/stopped/unavailable/attention; the body distinguishes reasons. Freshness uses a monotonic clock with budget `interval + 2*timeout + 5seconds`. JSON contains current observations and the last40 transitions, capped in memory. Initial observations, reason changes, failures and recoveries emit bounded `service_status` stdout events; stable cycles update the snapshot quietly. Fixed projected fields exclude upstream bodies/addresses/private exception text/credentials. Collection failure cannot stop checks; monitor health does not attest stdout delivery.

The in-memory40-transition history still resets with a new run UUID. D122 adds optional bounded local file retention for service transitions, described below. This is not a durable financial audit store or an off-device incident archive. Web API/framework events and worker journals remain separate sources. Never forward arbitrary raw Next stderr as sanitized telemetry. No external notification recipient/transport, reboot-persistent service or off-host watchdog is installed here. Only an independent process manager/external probe detects monitor/host death. A sleeping Mac also suspends checks. SIGTERM/SIGINT stop cleanly after bounded in-flight probes; rollback is stopping this process, with no product data change.

Validation covers actual HTTP malformed/status/timeout/redirect/body bounds, serialized cycles, deduplication/history limits, existing Facebook/TikTok attention and recovery, listener conflicts without target probes, real CLI failure/recovery and SIGTERM. Local runtime acceptance is distinct from production service installation.

## Optional retained service history (D122)

Set LABSD_MONITOR_LOG_ENABLED=1 with explicit LABSD_MONITOR_LOG_MAX_BYTES (1024–16777216) and LABSD_MONITOR_LOG_MAX_FILES (1–100). The example environment provides65536bytes ×4files, at most256KiB of segment contents; choose capacity for the deployment. This is capacity retention, not a guaranteed number of days. Reducing capacity may remove the oldest matching segments at startup/rotation; if an old segment exceeds a new smaller byte limit the journal refuses to proceed rather than silently altering it. Preserve needed diagnostic records before changing limits.

After claiming its unique health port, the monitor writes exclusively to project-local .agent-work/runtime/logs/services/<monitor-port>/events-<12digits>.jsonl. No operator-supplied directory or stdout/stderr ingestion is accepted. Each fixed service event is validated and fsynced before its sequence is acknowledged; directory0700/files0600, no symlink or hard-link segments. Mechanical rotation is shared with the existing worker journal; each formatter retains its own event vocabulary. Rotation prunes only exact segment filenames inside its own namespace and leaves unrelated files untouched. Never run two processes against the same namespace; the same-root monitor CLI derives it from its exclusively bound loopback port.

Restart starts a new segment and keeps retained older runs within the configured capacity. An interrupted last line is never appended to; for diagnosis read complete JSON lines and identify by monitorRunId+sequence, not sequence alone. SIGTERM closes the journal. Files persist across process restart, but local fsync is not an off-device/power-loss/PITR guarantee and no directory-fsync disaster-recovery claim is made. A bounded filesystem write can still stall on a stuck filesystem; an independent watchdog must detect a hung process.

When capture is enabled, /health includes logCapture with state and lastStoredSequence. It returns503 if the journal is unavailable or has not acknowledged the latest transition, even if the web target is healthy. Missing/replaced directory/file detection works on health inspection even during quiet cycles. Target probes and in-memory history continue; the storage failure latches until restart after fixing the path/capacity/permissions. Health acknowledges writes already completed, not that a future disk-full write will succeed. Do not blindly delete retained evidence to restore a green status.

Disabled capture preserves the prior monitor response shape and creates no journal. Raw webAPI/framework stdout collection, external alert delivery, reboot supervision, and off-device retention remain separate open work. This monitor journal contains status transitions only; never put financial transactions, cookies, tokens or arbitrary exception output into it.

Freshness is anchored to completion of the health probes before synchronous event writes, and recalculated after journal filesystem checks when serving health. Slow storage cannot renew an old observation. This does not eliminate filesystem stalls; an independent watchdog must detect a nonresponsive process.
