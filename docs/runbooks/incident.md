# Incident triage — Labs D x Partner

Use the exact deployed SHA/build ID, instance and target namespace; a dirty local checkout is not production evidence. Name the incident owner and record start time/timezone, affected capability and whether partners are seeing stale data, denied access or failed writes.

The optional [service monitor](service-monitor.md) automates repeated same-host health checks and exposes current status/recent transitions. Configure only installed lanes. Its status does not prove delivery to an external alert recipient or source completeness. For a page failure, use the displayed error reference plus time/route to find a `framework_error` event; see [page errors](../implementation/page-error-observability.md). Raw framework stderr remains outside sanitized events.

1. For an API failure, capture the response `X-Request-ID`, method, status and approximate time from developer tools/support diagnostics. Do not collect passwords, cookies, full invite/reset URLs, authorization headers, request bodies or private exports. With API observability enabled, find the matching `api_response` event in the selected instance's stdout collector. Match the static route template/status/time; an ID is a troubleshooting reference, never identity or permission evidence. Incoming IDs cannot choose the generated ID.
2. Check `/api/health` then `/api/ready`. Health200 only proves a responding web process. Ready503 means configured dependencies/binding/migration checks are unavailable, not that a payment failed or an import may be rerun safely. Check that instance's flags, DB reachability/pool pressure and required migration ledger against the frozen artifact. Never edit the binding or migration ledger merely to turn readiness green.
3. For source problems, inspect existing import activity/current-window coverage and the worker health/journal described in the imports and marketing runbooks. A healthy worker is not proof of complete source coverage. Preserve the last verified data and report source lag separately. Do not invent revenue from ad metrics, or count a missing source as zero sales.
4. For publication failures, inspect the independent activation state, staff authorization and original idempotency/approval/generation references. PUBLICATION_DISABLED is an operator control, not a request to log in again. Before retrying an ambiguous write, determine whether the original command committed using its existing immutable reference. Never issue a second financial adjustment to hide an uncertain result.
5. For containment, use the already authorized capability-specific disable path (publication or the affected source worker). Restart/redeploy every affected instance consistently; flags do not cancel in-flight work. Production changes, credential replacement and destructive recovery require the incident owner's explicit authorization and the release/secret workflow. Do not disable unrelated partner reads by default.
6. Record the cause, affected interval/data, corrective candidate SHA, verification receipt and reopening decision. A code rollback cannot reverse database/financial effects. Restore only through the backup/restore runbook into an approved target.

API events are best effort. Check `droppedSinceLastWrite`; nonzero means an incomplete log interval. A permanently blocked or broken stdout collector may never emit a recovery count, so monitor collector/process health separately. No continuous collector, retention period, alert destination or named production operator is installed by this runbook. Framework-generated responses, page/SSR errors and post-header stream failures currently lack API-wrapper events; their absence in the API log is not proof of success. Do not enable generic debug logging as a shortcut: dependency/framework logs have a separate redaction scope.
