# Identity/session recovery and rotation procedure

This portal uses invite-only username/password access after a deal. Recovery follows a previously verified contact channel and the existing staff/member flows. Do not reintroduce public signup or social login to recover an account.

## One member or suspected account compromise

Use the existing staff membership suspension/permission workflow for the selected partner and member, then its verified-contact reset flow when appropriate. Changes require current staff authorization, revision and fresh authentication. The account password change/reset transaction updates the credential, consumes the one-time intent where applicable, then calls `revokeIdentitySessions`; this advances the user fence/mutation clock and deletes that user's sessions. Membership changes invoke the same revocation mechanism. Do not delete a single browser cookie and call the account revoked, and do not manually edit sessions outside these transactions.

Acceptance on an isolated synthetic account: the old password and old signed session must fail; a consumed reset link must not work again; the new login must retain only the intended partner permissions; another member's account must remain valid. Existing tests cover these service paths, but a new production incident requires evidence for its actual target and affected session, not a citation to historical tests. Never put reset URLs or passwords into incident logs.

## Shared signing-secret replacement

The current credential binding digest is based on `credentials-v1` plus `BETTER_AUTH_URL`; it is not a hash of `BETTER_AUTH_SECRET`. A secret change therefore must not rewrite the namespace binding. All web instances and identity-using workers must receive the approved new signing-secret reference consistently through the secret-provisioning workflow. Current runtime caches config, so restart/redeploy is required. No rolling multi-key compatibility procedure is established here: do not claim uninterrupted sessions during a mixed-key rollout.

Before an authorized rotation, prepare a synthetic isolated drill on the same frozen candidate: log in under the old secret, rotate the injected value and restart, prove old cookies fail and new login succeeds, verify readiness/binding and account/partner isolation. D124 completed this drill against the local D120 web artifact with two isolated synthetic members; [full acceptance](../implementation/signing-key-rotation-acceptance.md) records the verified scope. It also demonstrated that restoring the old synthetic key revalidates a retained old session. A key change does not itself delete or transactionally revoke stored sessions. Plan user sign-in interruption and operator access recovery. Retain only secret-version references and receipts, never values. Revoke/invalidate existing sessions using an independently reviewed transactional procedure if the incident scope requires global session invalidation; a global-revocation admin command is not currently implemented. Do not restore a compromised old secret as a casual rollback—old signed cookies and retained sessions may become valid again.

A production rotation, global session invalidation or recovery-channel change is not executed by this document. Remaining acceptance: a reviewed global-invalidation procedure if needed, actual target secret store/operator, consistent rollout to every identity-using process and an agreed recovery window. D124 verifies sequential restarts in an isolated local target; it does not establish mixed-key rolling compatibility or production delivery. Database credentials and platform tokens have different scopes and must use their own owner/provisioning and post-rotation connection checks; never assume changing the portal key rotates upstream tokens.

Source authority: `src/server/modules/identity/credential-auth.ts`, `passwords.ts`, `revocation.ts`, and `src/server/modules/partners/access.ts`. These define behavior; this runbook does not grant a recovery bypass.
